# Миксы и «Моя волна» — ТЗ и как это устроено

Документ двойной: пока функция строится — это ТЗ и план подзадач; по мере готовности разделы переписываются в
описание того, как работает сделанное (в конце каждого раздела — статус). Исследование, из которого всё это выросло
(Spotify, Яндекс, open source, модели и источники похожести), — в разделе 12.

Связанные документы: [PLAN.md](PLAN.md) — ТЗ всего сервиса, [PROGRESS.md](PROGRESS.md) — что сделано,
[hub/API.md](hub/API.md) — контракт API (новые эндпоинты описываются там же, в ветке, где появляются).

## 1. Что строим

1. **Микс дня** — каждое утро у каждого пользователя новый плейлист из **50 песен**: часть знакомого (любимое, давно
   не слушанное), часть нового, похожего на его вкус. Песни **скачиваются заранее** (ночью, тихо) — микс играет офлайн
   и виден в приложении как обычный плейлист Navidrome. Микс живёт **до следующего микса**; при замене удаляются
   песни, скачанные ради него и так и не прослушанные (правило — раздел 6).
2. **Моя волна** — бесконечный поток под вкус пользователя: следующие песни подбираются на лету по тому, что он
   слушает, пропускает и ♥ сейчас. Можно запустить от трека или исполнителя («волна по треку»). Песни волны играют
   потоком с Хаба, скачиваются по ♥ или по полному прослушиванию (как «экономный» импорт, D9).
3. **Сбор данных о прослушивании** — всё, чего не хватает для персонализации, Хаб записывает сам: начало, пропуск
   (с секундой), полное прослушивание, ♥, «Не нравится», откуда запущен трек — для песен библиотеки и треков каталога,
   из приложения и из PWA.

Не делаем (решение владельца 2026-10-22): обучаемые модели ранжирования (данных мало), daylist с обновлением
несколько раз в день, обучение своей коллаборативной фильтрации на открытых датасетах.

## 2. Решения владельца (2026-10-22) — не переспрашивать

- M1 Только бесплатные решения. Неофициальные API (радио YouTube Music, Яндекс Музыка) использовать **можно и нужно**.
- M2 Наши прослушивания можно отдавать наружу, если это улучшает миксы (например, обратная связь «Моей волне»
  Яндекса). Без необходимости — не отдаём.
- M3 Нейросеть для звука — на **видеокарте** (RTX 5060 Ti 16 ГБ), модель уровня ~700 млн параметров.
  Ей прогоняются песни, о которых у карт похожести нет данных, и все кандидаты — для сравнения со вкусом.
- M4 Веса событий (решение владельца 2026-10-23): ♥ в нашем приложении **+1**, дослушал **+2**, пропуск раньше 30 с
  **−1**, пропуск позже — **от 0 до +2** по тому, сколько дослушал (см. раздел 5), «Не нравится» **−5**; **скачал
  сам — на вес не влияет** (до 2026-10-23 было: ♥ +3, своя загрузка +1, поздний пропуск до +1). **♥, поставленные импортом из Яндекса, не учитываются** (Хаб знает их: `imports.options_json.liked`).
- M5 Микс: 50 песен, скачивается для офлайна, живёт до следующего микса; непрослушанные скачанные — удаляются.
- M6 Ключ Last.fm — в `.env`: `LASTFM_API_KEY`, `LASTFM_SHARED_SECRET` (+ `LASTFM_APPLICATION_NAME`,
  `LASTFM_REGISTERED_TO`). Агент ключи не вводит и не выводит.
- M7 Можно попробовать «Мою волну» Яндекса с токеном из импорта (может не работать через VPN — тогда без неё).

## 3. Данные о прослушивании

### 3.1. Что было до T1
- Navidrome: `scrobbles` (каждое засчитанное прослушивание с временем; с 0.59), `annotation` (♥ `starred_at`,
  `play_count`, `rating`). Tempus засчитывает трек только после `min(50 %, 4 мин)`; **пропуски не доходят до сервера**,
  треки Хаба (`hub:<ref>`) не засчитываются вовсе.
- Хаб: загрузки (`download_items`: кто, что, явно или ради ♥), импорты (лайки/дизлайки Яндекса — дизлайки
  учитываются как «Не нравится», лайки — нет, M4), выборы файлов для прослушивания (`catalog_cache listen:*`).

### 3.2. Как устроено (T1 — Хаб и PWA; T3 — приложение; сделано)
Хаб записывает сам, чего не хватает: таблица `play_events` (`hub/app/plays.py`) — одно событие на строку:

| Поле | Что |
|---|---|
| `user_id` | пользователь Хаба |
| `ts` | время события (UTC, от клиента; Хаб правит явно неверное — больше часа в будущем или старше трёх календарных лет — на время приёма); будущее до часа не участвует до наступления ts |
| `kind` | `start`, `progress`, `interrupted`, `error`, `skip`, `finish`, `like`, `unlike`, `dislike`, `undislike` |
| `playback_id`, `device_id`, `listened_ms` | id попытки и устройства, накопленное измеренное время; итог берёт максимум checkpoints |
| `track_metadata` | снимок известных полей и provenance источников |
| `ref` / `nd_song_id` | трек каталога и/или песня Navidrome (что известно; Хаб дополняет второе по первому) |
| `position_s`, `duration_s` | где был плеер в момент события (для `skip`/`finish`) |
| `context` | откуда запущено: `mix:<id>`, `wave:<session>`, `album`, `playlist`, `search`, `liked`, `queue`, `other` |
| `client` | `app/<версия>`, `pwa`, `navidrome` (импорт scrobbles) |
| `event_id` | id от клиента — повторная отправка не дублирует (уникальный ключ `user_id + event_id`) |
| `launch_id`, `launch_origin` | только для аналитики (INSIGHTS.md §6.5), профиль, миксы и волна их не читают: один id на все события одного запуска списка (у волны — `wave:<session>`) и где запустили (`mix_page`, `mix_page_track`, `album`, `search`, `wave`…; словарь — `hub/API.md`); у старых событий и клиентов — `NULL` |

- **Определения:** `finish` — трек доиграл до конца сам или пользователь ушёл после ≥ 90 % длительности; `skip` —
  ушёл раньше (переключил, выбрал другой трек, закрыл плеер); пропуск «раньше 30 с» (вес −1) — `skip` с
  `position_s < 30`. Промежуточное (30 с … 90 %) — нейтрально. Пауза и перемотка внутри трека — не события.
- **API** (контракт полей — `hub/API.md`, «Listening data»): `POST /api/plays/events` — пачка до 500 событий; ответ
  всегда `200` с `{accepted, duplicates, rejected}`: плохое событие отклоняется одно и остаётся для диагностики,
  повтор доставленных событий ничего не дублирует. `ref` ↔ `nd_song_id` Хаб дополняет по
  файлу библиотеки (Deezer id), по загрузке или строке импорта, которые его принесли.
- **«Не нравится»** — таблица `dislikes` (трек: `ref`/`nd_song_id`; исполнитель: `artist_ref`; `source` — `app`, `pwa`,
  `yandex_import`), API `GET/POST/DELETE /api/dislikes`. Тот же трек по другому id — та же строка. События
  `dislike`/`undislike` из `/api/plays/events` ставят и снимают строку; отметка через `/api/dislikes` пишет такое же
  событие в историю. Для профиля правда — таблица `dislikes` (в ней и дизлайки Яндекса).
- **Дизлайки импорта Яндекса** — в `dislikes` с `source=yandex_import`: найденные в каталоге/библиотеке строки
  коллекции «Не нравится» (старые импорты перенесла миграция `d4e6b2a9c3f1`, новые пишет `imports/apply.decide`);
  не найденные не записываются (нечем их назвать).
- **Navidrome** — история прослушиваний есть в REST API Navidrome (не в Subsonic): `GET /api/scrobble?user_id=…
  &_sort=id&_order=DESC&_start=&_end=` → `[{id, mediaFileId, submissionTime}]` (проверено на 0.64.2; фильтра «id больше»
  нет, поэтому читается с конца до уже известного id). Раз в час (первый — через 2 мин после старта Хаба,
  `plays.scrobbles_loop`) Хаб входит под каждым пользователем (`/auth/login` его паролем из `users`, токен держится
  сутки: вход у Navidrome ограничен по частоте), берёт новые scrobbles (курсор — `navidrome_sync.last_scrobble_id`) и
  пишет их `finish` с `client=navidrome`, `event_id=nd:<id>`. Дубли с событиями приложения — тот же трек в пределах
  **5 мин + длительность трека** (Navidrome засчитывает на середине, приложение шлёт `finish` в конце): scrobble рядом
  с событием приложения сохраняется с признаком `superseded_scrobble` и исключается из скоринга и итогов;
  если событие пришло позже, Хаб помечает ранее записанный scrobble. Пользователь, которого Navidrome не пустил, пропускается до следующего часа.
- **Журнал ♥ (этап B):** `target_type=track|album|artist` (старым строкам миграция даёт track),
  `nd_album_id`/`nd_artist_id`, снимок `target_data` и причинная компенсация `reverts_event_id`.
  `favorite_subjects` хранит проверенные aliases и метаданные, состояние сворачивается по полному журналу
  пользователя, отдельно от окна скоринга. Повтор like сохраняет дату серии; unlike нейтрален; компенсация
  отменяет только своё решение и не отменяет более новое самостоятельное действие.
  Capability `favorite_compensation_chains_v1` дополнительно разрешает отменить компенсацию через её event_id:
  исходный ♥ и его дата восстанавливаются; два независимых отката требуют отмены обоих. Цепочки сверяются
  по пользователю и canonical typed target; неизвестные ссылки и циклы инертны. Доставка до target допустима.
  После изменения результата цепочкой mirror повторно доставляет итоговое состояние, а не kind компенсации. Писатели `/api/star`,
  ассистент (`assistant`/`assistant:bulk`) и загрузки используют общий `favorites.py`; старые клиентские дубли
  веса не добавляют. Окончательная ошибка загрузки компенсирует promise, явный unlike переживает stale job/retry;
  успешная ручная попытка восстанавливает обещанный ♥ только при отсутствии явного снятия.
- **Сверка ♥:** раз в час независимо от успеха scrobbles; успешный `getStarred2` сравнивает все три типа.
  Ошибка/неполный ответ не равны пустому списку. 24 ч отсчитываются от received_at последнего собственного
  решения/компенсации; дубли не сдвигают срок. Незавершённая доставка повторяется, pending без ND остаётся.
  Bootstrap сохраняет исходную дату старого ♥ один раз, не перезаписывает известный unlike; scrobble dedup
  помечает Navidrome finish и сохраняет synthetic like. Checkpoint — расширенный `navidrome_sync`.
- **♥ импорта не считаются** (M4): provenance song/album/artist хранится в `imports.options_json`
  (`liked`, `liked_album_ids`, `liked_artist_ids`) и проверенных aliases коллекций. Старые связи восстанавливаются
  через локальный Album/Track и ответы ND, неизвестные импортные album/artist не становятся собственными до
  проверки/явного действия. В интерфейсе импортные ♥ видны с provenance import.
  `plays.user_events(s, user_id, days, kinds=…, now=…)` возвращает только `ts <= now`.
- **PWA (T1, сделано):** мини-плеер страницы (`web/src/lib/listen.ts`; браузер и старые APK) шлёт `start` (когда пошёл
  звук и Хаб ответил, что играет не превью Deezer), `skip`/`finish` (переход, конец трека, закрытие плеера),
  `client=pwa`, `context` — экран, откуда запущен список (`album`, `search`, `playlist`, `other`). ♥ в PWA →
  `like`/`unlike`. События копятся в `localStorage` и уходят пачкой (`web/src/lib/plays.ts`): через 3 с после
  последнего и при уходе со страницы (`keepalive`). У строк треков каталога и библиотеки — «⋯»: «Не нравится» трек и
  исполнитель (повторно — снять), после отметки тост «Отменить»; играющий в мини-плеере трек пропускается
  (`web/src/lib/dislikes.ts`, `components/TrackMenu.tsx`).
- **Приложение (T3, APK 1.5.0):** `HubPlays` слушает каждый плеер сервиса (`BaseMediaService`) и шлёт `start` (пошёл
  звук), `skip`/`finish` (переход, конец очереди, смена очереди, закрытие сервиса; позиция между событиями плеера
  считается от последней известной) для всех музыкальных треков — песен Navidrome (`nd_song_id`) и треков каталога
  (`hub:<ref>` → `ref`). ♥ песни любым путём приложения (плеер, меню, панель выбора, уведомление) → `like`/`unlike`
  (звезда Navidrome — как раньше). `client=app/<versionName>`, `context` — поле `context` у элементов моста
  `playQueue` (необязательное, старые приложения его не читают): PWA ставит его каждому элементу —
  `routeContext()` экрана или явный аргумент `playTracks`/`playHubItems`/`playMixed` (`mix:<id>` у будущих страниц миксов);
  старый мост `play` (только `song_id`) его не несёт → `other`. События лежат в файле на
  телефоне без удаления старых событий по лимиту и уходят пачками до 500: через 5 с после последнего, при сбое — через 30 с … 30 мин, каждые 15 мин
  фоном (`HubSyncWorker`); 401 — вход заново, как у других запросов; 404 (старый Хаб) — события ждут, повтор раз в 6 ч.
  **«Не нравится»** — строка меню трека и кнопка 👎 рядом с ♥ в плеере: `POST /api/dislikes` (`client=app/…`),
  играющий трек пропускается, снекбар «Отменить» → `DELETE`; без сети отметка уходит событием `dislike`/`undislike`.
  При рестарте checkpoint той же попытки может быть продолжен по совпадающей позиции; иначе записывается `interrupted`, не `skip`.

- **Итоги:** `GET /api/plays/summary` считает по календарным датам выбранного IANA timezone. Для измеренной
  попытки порог — 30 с или половина трека короче минуты. Scrobble — отдельное пороговое свидетельство, не
  точное время; старые `position_s` не превращаются в секунды прослушивания. Период определяется началом
  попытки, `first_observed_at` — первая известная запись, не начало прослушивания в жизни. `track_metadata`
  сохраняет известные сведения и их источники независимо от удаления файла/cache. Неизвестное не выдумывается.
  Старые данные не переписываются; трёхлетний предел проверки входной даты не является сроком хранения.

- **Запуски списков (INSIGHTS.md §6.5, 2026-10-31):** PWA даёт каждому новому списку плеера страницы и каждому вызову
  моста `playQueue` новый `launch_id` (`plays.newLaunch`; волна — `wave:<id>`), он сохраняется при перезагрузке
  страницы; `launch_origin` — по экрану (`plays.launchOrigin`) или явно («Слушать всё» микса — `mix_page`, тап по треку
  микса — `mix_page_track`). Элементы `playQueue` несут их тоже (приложение начнёт читать на этапе 5 INSIGHTS).
  Capability `launch_events_v1` в `/healthz`.

Статус: T1 сделан 2026-10-22 (Хаб, PWA, история Navidrome, дизлайки Яндекса); T3 (приложение) сделан 2026-10-22 (APK 1.5.0).

## 4. Карты похожести и нейросеть

### 4.1. Источники кандидатов (T4, сделано; проверены вживую 2026-10-22)
| Источник | Генератор микса | Как (код — `hub/app/mixes/sources.py`) |
|---|---|---|
| **Радио YouTube Music** — основной | «Похожее» `ytm_radio` | сид ищется в YTM (`youtubei/v1/search`, фильтр «Songs», клиент WEB_REMIX без входа, версия — как у поиска в `providers/ytdlp.py`; совпадение по `matching.score` ≥ `confirm_threshold`), затем `youtubei/v1/next` с `playlistId=RDAMVM<videoId>` → строки `playlistPanelVideoRenderer`: название, «исполнители • альбом • год» (у клипа — «канал • просмотры»), длина; сам сид выкидывается. ~50 треков за ~1 с |
| **Last.fm** (`LASTFM_API_KEY`, M6) | «Похожее» `lastfm_similar`, «Незнакомое» `similar_artists`, теги для названия | `track.getSimilar` (30 на сид), `artist.getSimilar`, `artist.getTopTags` (у `track.getTopTags` русских треков тегов почти нет); ≤ 5 запросов/с, `autocorrect=1`. `error 6` («не найдено») — пустой ответ (кэшируется), другие ошибки — источник недоступен. Нет ключа — генератор выключен (`off`) |
| **Deezer** (без ключа) | «Похожее» `deezer_radio`, «Незнакомое» `similar_artists`, «Новинки» `new_releases`, онбординг | `DeezerClient.get_artist_radio` (`/artist/{id}/radio`, 50 треков с `rank`), `get_artist_related`, `get_artist_albums` (по дате), `get_artist_top`, `chart_artists` (`/chart/0/artists` — страна по адресу запроса). Ответы — сразу треки каталога, без сопоставления |
| **Яндекс `tracks/{id}/similar`** (без токена) | «Незнакомое» `yandex_similar` | трек находится поиском Яндекса (совпадение ≥ `auto_threshold`); похожих ~10, в основном малоизвестные исполнители |
| **Яндекс «Моя волна»** (M7) | `yandex_wave` | `rotor_station_tracks('user:onyourwave')` с токеном, сохранённым импортом Яндекса (`imports.token_enc`, «Обновить»), до 6 пачек. Без токена ротор отвечает `Cannot build either user id` — генератор выключен; отказ Яндекса (регион, VPN) — ошибка генератора, микс собирается без него. Обратная связь Яндексу не отправляется (ни миксом, ни волной) |

Всё, что пришло как «исполнитель — название», сопоставляется с каталогом (`hub/app/mixes/resolve.py`): сначала
библиотека (`find_existing`; песня без записи Deezer — трек `source="nd"`, `ref` `nd:<song>`), затем `source_map`
(что этот id источника оказался в каталоге — общая память импортов; источники `ytm`, `lastfm`, `yandex`), затем поиск
Deezer + `match_catalog`. Берётся только уверенное совпадение (`auto`): микс скачивает то, что предлагает, и ошибка
стоит загрузки. Ответы источников кэшируются в `catalog_cache` на 7 дней (`mix:*`), «Моя волна» — никогда (личная).
Карточки найденных треков — `mix:track:<ref>` (30 дней).

### 4.2. Нейросеть для звука — сервис `embedder` (T2, сделано)
Отдельный контейнер `homemusic_embedder` (`embedder/`: FastAPI, свой `pyproject`/`uv.lock`, PyTorch 2.11 + CUDA 12.8 —
первая сборка с ядрами Blackwell sm_120). Модель — **MuQ-MuLan-large** (`OpenMuQ/MuQ-MuLan-large`, пакет `muq`,
~700 млн параметров, 24 кГц, веса в fp32 по README модели, на GPU — под fp16-autocast (ниже); веса CC BY-NC 4.0 — личное некоммерческое использование):
вектор звука и вектор текста (512 чисел, длина 1) в общем пространстве. Текст — английский или китайский
(русский запрос Хаб сначала переводит LLM).

**Как считает.** Из файла библиотеки берётся 30 с из середины (`EMBEDDER_CLIP_S`), превью Deezer (30 с) — целиком;
ffmpeg → моно 24 кГц. Фрагмент режется на куски по 10 с (как в `muq`), куски всей пачки (до 16 песен,
`EMBEDDER_BATCH`) идут через звуковую часть модели вместе по 4 (`EMBEDDER_CLIP_BATCH`), вектор песни — среднее
векторов её кусков, нормированное. Пока модель считает пачку, следующая пачка уже скачивается и декодируется
(8 загрузок параллельно).

**Устройство.** Видеокарта общая (на ней же свои задачи владельца), поэтому модель загружается только при работе:
при каждой загрузке сервис смотрит свободную память GPU по драйверу (NVML, `nvidia-smi`) — ≥ 5 ГБ (`EMBEDDER_MIN_FREE_GPU_MB`) → на GPU, иначе
модель не грузится и ждёт карту (`GpuBusy` в `/healthz`, попытка раз в `EMBEDDER_RETRY_S` = 60 с; запасного пути на CPU
нет: там ~7 ГБ RAM и в 50 раз медленнее, а RAM общая с Windows); после 5 минут без работы (`EMBEDDER_IDLE_UNLOAD_S`) модель
выгружается. `EMBEDDER_DEVICE=cuda|cpu` — принудительно (CPU — 6 потоков, `EMBEDDER_CPU_THREADS`, и поднять `mem_limit`).
Веса (~2,5 ГБ, `pytorch_model.bin`) скачиваются с Hugging Face при первой загрузке в том `embedder-models`,
не в образ и не в git. GPU в контейнер — `deploy.resources.reservations.devices` nvidia (Docker Desktop + WSL2).

**Загрузка модели** (`load_muq_mulan` в `embedder/app/models.py`, 2026-10-23). `MuQMuLan.from_pretrained` из пакета
`muq` сначала скачивает и целиком загружает в RAM обе предобученные подмодели (MuQ-large 1,3 ГБ и XLM-RoBERTa 1,1 ГБ),
затем читает поверх них 2,5 ГБ весов MuQ-MuLan — всё в fp32 на CPU — и только потом модель переносится на GPU: пик
~6 ГБ RAM процесса и ~5 ГБ кэша страниц. В WSL2 всё это ложится в vmmem и в лимит виртуальной памяти Windows
(файл подкачки 2 ГБ): vmmem рос с 6 до 14–17 ГБ, Docker Desktop падал, а CUDA при почти исчерпанном лимите
отказывала в памяти и на пустой карте («CUDA out of memory»). Теперь подмодели создаются только по конфигам (их веса
всё равно перезаписываются), модули создаются сразу на GPU (`torch.device("cuda")`), чекпойнт открывается через
`mmap` и копируется в параметры потензорно (`load_state_dict`, одна копия весов), после чтения его страницы
выбрасываются из кэша (`posix_fadvise DONTNEED`). Контейнер ограничен `mem_limit: 4g` без swap — разросшийся процесс
убьёт ядро внутри контейнера, а не Docker целиком; Хаб в это время строит миксы без звука.

**Видеопамять тоже съедает лимит Windows.** В WSL2 память, которую CUDA берёт на карте, списывается из лимита
виртуальной памяти Windows (commit): замер при работе с пачкой клипов 24 — карта +7,5 ГБ, контейнер +1,3 ГБ RAM, а
свободная виртуальная память Windows −5,1 ГБ (с 7,4 до 0,9 ГБ в пике). Скорость от размера пачки клипов почти не
зависит (64 песни: 24 → 14,3 песни/с, 7,7 ГБ видеопамяти у torch; 12 → 13,9, 5,2 ГБ; 8 → 13,9, 4,3 ГБ;
4 → 14,1, 3,4 ГБ), поэтому `EMBEDDER_CLIP_BATCH=4`. Через 5 минут без работы модель выгружается и отдаёт и карту, и лимит.

**Точность.** Входные признаки MuQ — сырая (не логарифмическая) мел-мощность, нормированная линейно: на громкой
музыке она выходит за предел fp16 (65504), и под простым fp16-autocast вектор получался NaN у 58 из 64 песен
библиотеки. Поэтому мел-спектрограмма и первые свёртки MuQ идут в fp32, остальная звуковая башня — под fp16-autocast
(`EMBEDDER_PRECISION=fp16`, по умолчанию; `bf16`, `fp32`). Сравнение с fp32 на 64 песнях библиотеки: косинус
вектора fp16 и fp32 ≥ 0,9999997, 5 ближайших соседей каждой песни совпадают полностью, разница попарных похожестей
≤ 0,00015 (bf16 — ≤ 0,0013).

**Очередь и хранение.** Свой SQLite в томе `embedder-data` (`/data/embedder.sqlite3`), таблица `items`: ключ,
источник (`url` или `path`), статус `queued → running → done | error`, попытки, вектор (`float32`), имя модели.
Очередь переживает рестарт (`running` при старте возвращаются в `queued`). Ошибка одной песни не трогает остальные:
нет файла, 4xx, не декодируется, больше 60 МБ → `error` сразу; сеть, 5xx/429, сбой модели (нехватка памяти GPU) →
повтор через 60 с × попытка, всего 3 попытки. Векторы сравниваются только внутри одной модели (смена модели —
векторы считаются заново тем же `POST /embed`).

**Доступ.** Только из сети compose: порт наружу не публикуется, Хаб зовёт `http://embedder:8090` (`EMBEDDER_URL`).
Если в `.env` задан `EMBEDDER_TOKEN` — все запросы, кроме `/healthz`, с заголовком `Authorization: Bearer <токен>`.
Сервис не ответил — миксы и волна строятся без звукового слагаемого (это делает Хаб, T4).

`v′ = norm(v − μ)`, где μ — среднее всех корректных `done`-векторов текущей модели. Один снимок в памяти
обновляется при записи вектора, возврате готового ключа в очередь или смене модели. `space_id` — хеш содержимого
снимка и имени модели; одинаковые данные после рестарта сохраняют id. Старые снимки и пользовательские профили
не кешируются. Запрос с прежним id после изменения снимка получает **409**
`{detail: {code: "stale_space", space_id, model}}`: нужно заново вызвать `/v2/profile` и пересчитать геометрию сессии.
Внутри каждого запроса координаты и центры используют один снимок.

`/v2/project` (INSIGHTS.md §8): оси — PCA двух главных компонент **центрированных** векторов `v′` (повторно центрированных
по их среднему). `basis="global"` — по всем корректным векторам снимка (оси общие для всех пользователей, стабильны, пока
не менялся снимок; кэш осей в памяти по `space_id`), `basis="keys"` — по `fit_keys` (личная раскладка; без `fit_keys` — 422).
Знак оси детерминирован: наибольшая по модулю координата оси положительна. `explained` — доли дисперсии двух осей (ось без
дисперсии — нулевая, доля 0). Центр грани проецируется как точка; `facet_cos` — косинус `v′` к каждому центру в порядке
`facets` запроса. Лимиты (до 5000 ключей и `fit_keys`, до 5 граней, центр ненулевой и размерности пространства) — 422;
старый `space_id` — 409 `stale_space`; ключи без вектора — в `missing`. Модель не загружается.

Положительный вес — конечное число от 1 до 1 000 000 (повторные ключи суммируются), до 5000 элементов каждого
списка. Ключи — 1–300 символов; центр — до 4096 конечных координат от −1 до 1, ненулевой, размерности снимка;
до пяти граней. Нарушения дают 422. Нулевой residual и некорректный вектор пропускаются и попадают в `missing`;
`diagnostics = {available, zero_residual: [key], invalid: [key]}` уточняет причину для запрошенных ключей.
При повреждённых размерностях используется самая частая корректная размерность модели (равенство — меньшая).

Грани — взвешенный spherical k-means: самый тяжёлый ключ, затем самый далёкий, равенства по ключу;
`k ≤ min(5, 1 + floor(n/15))`, рост прекращается при улучшении среднего взвешенного cosine менее 0,03.
Грани легче 8% объединяются с ближайшей; `weight` — доля положительного веса, `id` стабилен по составу,
`members` сортированы. Названия по исполнителям формирует потребитель по `members`, LLM не используется.
`pos = max cos(v′, facet)`, `neg = max(0, max cos(v′, negative))`, `score = pos − 0,5·neg`;
пустой положительный или отрицательный набор даёт 0 для своего слагаемого.

Клиент Хаба добавляет `profile_v2`, `similarity_v2`, `vectors_v2` с typed-ответами и пачками кандидатов/векторов.
404 старого сервиса, недоступность и некорректный ответ дают обычный `EmbedderDown`; 409 или смена пространства
в ответе — его подкласс `EmbedderSpaceExpired`. Частичный ответ пачек при таком отказе не возвращается.
Потребители v1 пока не переключены; явное обновление профиля и fallback выполняет вызывающая сторона.

## 5. Профиль вкуса (T4, сделано — `hub/app/mixes/taste.py`)
- **Из чего (промежуточный v1):** playback-события `play_events` за год (раздел 3.2), постоянное собственное состояние ♥
  из полного журнала `favorites.snapshot` (без запроса Navidrome при расчёте; импортные ♥ не считаются, M4),
  его собственные загрузки (`download_items` `done`, не тихие: не только
  ради ♥, не импорт, не микс), «Не нравится» из таблицы `dislikes`.
- **Вес** (M4, 2026-10-23) × `0.5 ^ (дней / 30)`: ♥ +1 один раз с начала текущей непрерывной серии;
  повторный like её не омолаживает, unlike нейтрален. Старый действующий ♥ сохраняет состояние, но за пределами
  окна скоринга веса не даёт. До этапа D сохраняются календарные веса v1:
  `finish` +2, `skip` с `position_s < 30` −1, «Не нравится» −5, `start` — 0. `skip` после 30 с — от 0 до +2
  (`taste.skip_weight`): x = (позиция − 30) / (длительность − 30) — доля трека после первых 30 с, вес — гипербола
  2·x / (1 + 3·(1 − x)): медленно в начале, круто в конце (x = 0,5 → 0,4; 0,75 → 0,86; 0,9 → 1,38; 1 → 2).
  Своя загрузка веса не имеет: трек в профиле (`downloaded` — для «Тайника» и запасных сидов, «знакомое») с баллом
  остальных событий, без них — 0; «Любимое» (балл > 0) его не берёт, отрицательным (балл < 0) он не считается.
  Длительность — из события (`duration_s`), без неё — файла библиотеки или трека каталога; неизвестна — 0.
- **Трек** знают по `ref` и/или песне Navidrome (дополняются друг другом, `plays.Ids`) и по отпечатку
  «исполнитель|название»; ключ — `nd:<song>`, если песня в библиотеке (это и ключ её вектора в `embedder`), иначе
  `ref`. Профиль — «трек → балл», «исполнитель → балл» (сумма по его трекам; исполнитель — нормализованное имя) и
  «сколько раз исполнителя дослушали» (`finish` и `skip` ≥ 30 с — для правила «Незнакомого»).
- **Сиды** — до 8 (`mixes.seeds`) треков с наибольшим положительным баллом среди тех, с кем было событие за 30 дней,
  не больше 2 одного исполнителя; нет таких — ♥ и свои загрузки, новые первыми; нет и их — по 2 топ-трека
  исполнителей, выбранных на «Что вы слушаете?» (`mix_settings.artists_json`, Deezer `artist/{id}/top`).
- **Вкус по звуку** — профиль «ключ → балл» уходит в `embedder` `/similarity`: центр положительных (веса — баллы) и
  центр отрицательных (пропуски, «Не нравится»), у кандидата `sim = cos(к положительному) − 0.5·cos(к отрицательному)`.

### 5.1. Профиль вкуса v2 — контракт и состояние внедрения (2026-10-28)

Этот раздел фиксирует принятую модель и состояние её внедрения. Реализация v2 и её потребители доступны в коде,
с 2026-10-28 v2 включён на рабочем Хабе (`mixes.taste_model: v2`, откат — `v1`; default в коде — v1).
Модель v1 описана в §3.2, §4.2, §5 и §6–7.
Решения владельца: без календарной утечки; насыщение повторов; ранний skip только штрафует; unlike нейтрален;
обычный вес ♥ ассистента, включая массовые; журнал ♥ треков, альбомов и исполнителей; отдельный QA пользователь;
P1–P5 только в offline replay. Базовые M4 сохраняются: finish +2, ранний skip −1, поздний skip по `skip_weight`
из §5, собственный ♥ трека +1, явный дизлайк −5, загрузка 0, start 0.

**Время и активность.** Расчёт — чистая функция снимка данных с явными `now`, моделью и timezone из
`Settings.timezone`/`TIMEZONE`; хранение дат UTC, границы дней местные. До любых сумм отсекаются другой
пользователь, известный QA/debug трафик и события с `ts > now`. Не объявлять старые события тестовыми только
по догадке о дате или версии клиента и не удалять историю.

- За день `d` считать разные канонические треки, услышанные ≥30 с (finish/scrobble, skip ≥30 с;
  старый finish без позиции означает завершение, полное завершение известного короткого трека тоже считается),
  плюс разные типизированные объекты с реальным собственным переключением ♥/«Не нравится», включая снятие.
  Aliases `ref`/ND объединяются; повторы одного трека не ускоряют часы, объект действия даёт не более единицы
  за день. Прослушивание и действие над той же песней могут дать две единицы.
- `m_d = услышанные треки + объекты с действиями`, `u_d = min(1, m_d/5)`. Импорт, дубликат состояния,
  компенсация отказа и повторная сверка не создают новую активность.
- Возраст `A(e) = sum(u_d)` по местным дням строго после дня события, включая доступную часть сегодняшнего
  дня; внутри дня возраст 0. Вес `w = 0.5^(A/30)`, без календарной утечки. Суммы скоринга используют события
  с `w ≥ 0.01` и календарным возрастом не более трёх лет; активность считается по всему трёхлетнему окну
  до отсечения по весу. Срок приёма клиентской истории планируется расширить до трёх лет.
- Окно положительных событий для сидов — 30 активных единиц. Отдых кандидатов 3 дня, «Любимого» 7 дней и
  «Тайника» 60 дней остаётся календарным. У раннего skip нет отдельного отдыха. После 45 дней тишины веса
  и активный пул сидов сохраняются, кроме независимой границы трёх лет; выбор восьмёрки может измениться
  из-за ротации по местной дате.

**♥ как состояние трёх типов.** Источник истины — журнал like/unlike; звезда Navidrome — его сверяемая копия.
Профиль читает локальные события, aliases и метаданные без обращения к Navidrome/Deezer. Планируется
расширяющая миграция без удаления истории и [совместимое расширение API](hub/API.md#planned-compatible-extension-typed-favorite-events-not-implemented):
`target_type=track|album|artist` (по умолчанию track), соответствующие ND id, ограниченный снимок метаданных,
`reverts_event_id` для причинной компенсации; start/skip/finish разрешены только для трека.

Состояние по каждому пользователю и каноническому типизированному объекту сворачивается в стабильном порядке
`(ts, received_at, id)` по всей истории ♥, отдельно от трёхлетнего окна скоринга. Один непрерывный like даёт
один вклад с даты начала серии; повтор like не омолаживает его. Unlike убирает вклад без минуса.
Компенсация отменяет конкретное отказавшее решение, включая позднюю доставку, и не отменяет последующее
самостоятельное решение другого устройства. Старое действующее ♥ сохраняет знакомость/«Тайник», но за
пределами окна/порога веса его вклад 0; неизвестная дата первоначальной звезды фиксируется один раз с provenance.

| Собственное действующее состояние | Вклад и применение |
|---|---|
| ♥ трека | +1 × w к положительному весу трека, знакомость, пул «Тайника» |
| ♥ исполнителя | +1 × w к `A_artist` |
| ♥ альбома | +0.5 × w к `A_artist` основного исполнителя; песни альбома знакомы и входят в «Тайник», без трековых +1 |
| ♥ ассистента | Те же веса; `client=assistant`, `context=assistant` либо `assistant:bulk` — только происхождение |
| Звёзды импорта | Не собственный сигнал для всех трёх типов, пока нет собственного решения (M4) |

API, ассистент, загрузки и сверка должны пользоваться общим сервисом журнала. Неуспех окончательной операции
компенсирует только её актуальное решение; временный retry не меняет вкус. Снятие pending ♥ отменяет желание,
поздний импорт или старая попытка не возвращают его. Сверка раз в час сравнивает все три типа и ждёт 24 часа
после `received_at` последнего собственного решения/компенсации объекта (не playback и не дубликата).
Ошибка/неполный ответ Navidrome не равен успешному пустому списку. Baseline переносит только отсутствующие
старые собственные звёзды с их датами, не воскрешает unlike; импортное и pending состояние без песни защищены.
Профиль при недоступном Navidrome остаётся тем же. Точный протокол публикуется вместе с реализацией этапа B.

**Баллы и потребители.** Для трека раздельно хранить положительный вес, отрицательный вес, даты положительного
сигнала/прослушивания, heard30, собственные liked/downloaded и album_liked; знакомость не выводить из наличия строки.
`P_raw` — сумма положительных M4 × w и текущего собственного трекового like × w;
`N` — сумма модулей отрицательных сигналов с их весами. `sat(x)=x` при `x≤2`, иначе
`sat(x)=2+2*ln(1+(x-2)/2)`; `s=sat(P_raw)-N`. Например, 30 finish без затухания дают `sat(60)≈8.802`.
Ранние skip не насыщаются. Действующее «Не нравится» остаётся постоянным явным фильтром (трек/исполнитель).

`A_artist = sat(sum(max(s,0))) - 0.5*sat(sum(max(-s,0))) + own_artist_like*w + 0.5*sum(own_album_like*w)`
по основному исполнителю. Трек знаком при ≥30 с/finish, собственном ♥, сохранении через альбом или собственной
загрузке; один start, ранний skip или дизлайк знакомости не даёт. Fallback исполнителя >5 прослушиваний за
три года сохраняется. Ранний skip сам по себе не включает трёхдневный фильтр полноценного прослушивания.

Отрицательный `s` не исключает кандидата ни в `keep`, ни в «Тайнике»: добавляется штраф `0.5*max(s,-4)`
(до −2). С учётом технических фильтров §6.1 исключение по вкусу — только явное «Не нравится».
Единый score микса и волны: вклад генераторов + `1.5*m*sim + 0.2*популярность`, плюс указанный штраф при `s<0`
и `0.3*max(A_artist,-3)` при `A_artist<0`. «Любимое» — знакомые `s>0` после 7 календарных дней;
«Тайник» — свои ♥/загрузки/песни лайкнутых альбомов после 60 календарных дней, с порядком местного дня.
Зрелость `E=sum(max(s,0))`, `m=min(1,E/20)` уменьшает только звуковое слагаемое и определяет долю онбординга.

**Грани и сиды.** Сырые векторы сохраняются, `/text` остаётся прежним. Для звукового профиля
`v'=norm(v-μ)`, где μ — среднее всех done векторов текущей модели. Нулевой остаток — missing, без NaN.
Модель и снимок μ задают `space_id`; профиль, кандидаты и векторы сессии используют один снимок.
Добавочные `/v2/profile`, `/v2/similarity`, `/v2/vectors` сохраняют v1 API.
Грани — weighted spherical k-means с детерминированным стартом, `k≤min(5,1+floor(n/15))`, остановкой прироста
среднего cosine <0.03 и слиянием граней <8%; равенства разрешаются стабильным key. Положительные члены имеют `s≥1`.
`sim = max cos(v',грань) - 0.5*max(0,max cos(v',отрицательный трек))`;
отрицательные — явный dislike или `N≥2`; пустая сторона даёт 0. Это локальный штраф, без общего центра пропусков.

До 8 сидов: `s≥1` и положительный сигнал с `A≤30`; start/unlike/ранний skip свежесть не обновляют.
Места — по весу граней (доля ≥15% получает хотя бы одно), внутри — выборка без повторов по s с seed
`hash(user_id,местная дата,версия)`, ≤2 на исполнителя. `round((1-m)*8)` мест резервируется онбордингу;
незаполненные места перераспределяются. Fallback собственных ♥/загрузок разрешён только при отсутствии
положительных событий в 30 активных единицах, а не при недостающих метаданных; онбординг и загрузки — явные
исключения порога `s≥1`. Без embedder — одна условная грань, без звука; top_artists учитывает значимые грани.
Волна получает свежий профиль после каждого next, учит события один раз по event_id и фиксирует версию модели
в сессии. Сессионные положительные веса соответствуют M4; unlike снимает только like, сохраняя finish.

**Replay и включение.** Offline replay — отдельное подключение SQLite `mode=ro` + `query_only`, без миграций,
sync, сетевого обогащения, загрузок и публикации плейлиста. Срез `ts≤T`; честный available-at replay дополнительно
ограничен `received_at≤T`. Исторические состояния ♥/дизлайков/онбординга/загрузок и векторы не подменяются
сегодняшними; недостающие данные явно помечаются. Сравниваются сиды, top20 «Любимого», исполнители, грани,
sim/score и AUC finish против раннего skip в подсунутом контексте; нехватка классов даёт AUC=null с причиной.
P1–P5 доступны только как offline варианты: P1 — пропуск <3 с, второй подряд в пределах 20 с в выбранном
самим списке, получает вес 0; P2 — ранний skip выбранного самим трека −0.5; P3 — ранний skip любимого с `s≥4`
получает −0.5 без сессионного штрафа исполнителю;
P4 — сглаживание раннего skip между 10 и 30 с; P5 — finish подсунутого трека ×0.75. Рабочие M4 они не меняют.

Этап D реализует чистый расчёт `app.mixes.taste_math.calculate_profile(snapshot, now=..., timezone=...)`
и пакетный локальный `app.mixes.taste_snapshot.load_snapshot`. У v2 отдельно доступны P/N, знакомость,
зрелость, positive weights/negative keys для геометрии и активный пул сидов. `build_profile` сохраняет v1
по умолчанию; явный `model="v2"` читает локальный снимок без сетевого обогащения. Флаги конфигурации
`mixes.taste_model: v1` и `taste_shadow: false` сохраняют безопасные defaults. Этап F подключает выбор модели
к сборке микса и новым сессиям волны; включение v2/shadow на рабочем Хабе относится к G.

Consumers v2 используют отбор до восьми сидов по весам граней и локальному дню, с резервом онбординга по
зрелости; неизвестные имена дозаполняются только у выбранного небольшого пула. Сохранённые песни альбома и
собственный catalog artist-like могут дать fallback без искусственного трекового score, если свежего
положительного сигнала нет. Score общий для микса/волны; ранний skip штрафует и не создаёт запрет/знакомость,
отдых 3/7/60 дней использует last_heard. Геометрия передаёт только центрированные векторы одного space_id:
409 сбрасывает все координаты операции и даёт один retry, затем fallback без звука.

Wave state v2 сохраняет модель, обработанные event_id, исходные сигналы/веса и сведения о пространстве.
Каждый next сначала пишет события, затем читает свежий профиль и пересчитывает pool/out. Unlike снимает только
like-вклад, finish/поздний skip остаются; отрицательный звук берётся по ближайшему отрицательному треку.
Старый JSON остаётся v1, его уже сохранённые journal ids до даты state считаются обработанными. Изменение
config действует на новые сессии: действующая сессия сохраняет модель и после рестарта, а координаты всегда
перестраиваются из исходных ключей в актуальном пространстве. Повтор события не усиливает learn/штраф/радио;
event_id, уже закреплённый за другой wave-сессией, не переносится между сессиями.

**Диагностика shadow.** При `mixes.taste_shadow: true` сборка микса снимает локальные данные после импорта
scrobbles, до сетевого обогащения профиля, в отдельной сессии. V1 baseline и v2 рассчитываются по одному снимку
и времени; это локальный baseline с исправленным журналом, а не точное воспроизведение обогащённого online v1.
Используется копия пула кандидатов активных генераторов до фильтрации (первые 500 кандидатов в исходном порядке).
Отчёт в `Mix.stats_json.taste_shadow` содержит ограниченные решения `keep` с причинами, ранги и вклады без звука,
локальные seeds и отдельно фактически использованные active seed keys, избранное и агрегаты профиля. Эти данные
относятся к пользователю, поэтому подробный отчёт и снимки истории не публикуются в репозитории.

Shadow не запускает повторную сборку, генераторы, LLM или задания embedding и не пишет историю. Для звукового
сравнения `/v2/shadow` делает атомарную копию готовых векторов и считает v1 raw-center и v2 centered-facet на
одном снимке без inference. Ранжируются только кандидаты с обеими оценками; отсутствующие векторы кандидатов и
профиля перечисляются отдельно, а не заменяются нулями. При отсутствии сервиса, старой версии или таймауте 5 с
сохраняется отчёт без звука. Ошибки диагностики не отменяют основную сборку; при выключенном флаге снимка нет.

Локальные seeds не включают cold, сетевое обогащение и фильтр metadata. При полном пуле до 500 кандидатов shadow
использует временные raw/centered координаты из того же снимка для повторного select/order на копиях, отдельно
ограничивая sound первыми 300 прошедшими фильтр кандидатами каждой модели; missing даёт штатный fallback.
При усечённом пуле или превышении лимита ответа по координатам итоговый выбор не вычисляется. Это сравнение одного
замороженного пула и текущих готовых векторов, без альтернативных генераторов и сетевого обогащения; оно не доказывает
качество полной политики или готовность включения v2.

Изолированный QA на копии БД проверил v2 mix, wave, early skip без Dislike, duplicate после рестарта процесса и
сохранение модели сессии при смене config. В этом сценарии генераторы/каталог синтетические, Navidrome sync и
закрытие предыдущего mix заглушены, prefetch отключён. Отдельно получен ограниченный реальный пул YTM/Deezer без
персональных credentials, с выключенными sync/cleanup/LLM/prefetch и embedder. Ещё одна проверка получила v1/v2
sound на сохранённых MuQ-векторах, но с синтетическими кандидатами; в смешанном пуле покрытие звуком было низким.
Реальное audio/text inference на CUDA прошло отдельно на синтетических данных после освобождения памяти GPU.
Эти проверки не составляют единую цепочку с реальными генераторами, inference, playback и публикацией плейлиста;
QA и rollout gates остаются открытыми.

Readonly replay запускается из `hub/` на сохранённой копии журнала:

```powershell
uv run python -m app.mixes.evaluate --db saved.sqlite3 --until 2026-10-27T12:00:00Z --user-id 1 --model v2 --seed 42 --timezone Europe/Moscow --output replay.json
```

Допустимы `--model v1|v2|P1|P2|P3|P4|P5`, `--mode available-at|occurred-at` (первый по умолчанию),
`--exclude-user-id ID` для явно известных QA аккаунтов. База открывается `mode=ro` + `query_only`;
создаётся только указанный JSON. Текущие изменяемые таблицы не используются для восстановления прошлого:
исторический state строится только из журнала. Алиасы и metadata берутся из доступных событий. Отсутствие
старой истории снятий, метаданных, векторов, граней и вклада генераторов отмечается в `limitations`/`null`.
Выход сравнивает eligible пул сидов (online-ротация F — отдельный от replay шаг), top20 по score и исполнителей с
локальным v1 baseline после исправлений B. AUC измеряет только score истории перед исходом, а не качество
полной рекомендательной политики; собственный оцениваемый исход исключён, bootstrap идёт по местным дням.

Порядок программы: A — документы/QA; B — журнал и писатели; C — клиенты с capability gating; D — модель/replay;
E — геометрия; F — потребители/волна; G — приёмка/shadow/включение. Изначально рабочая модель v1; v2 сначала
считает диагностическую альтернативу по тому же снимку без повторных загрузок, LLM и публикации. Затем —
включение после зелёных тестов, QA сценариев и объяснимых diff; малая выборка AUC не блокирует выпуск.
Откат — v1 и новые сессии волны, с сохранением совместимого Хаба, расширенной схемы и всей истории.

## 6. Микс дня (T4 — Хаб, сделано; страница — T5, приложение — T7)
Код — `hub/app/mixes/` (`build.py` — сборка, `core.py` — расписание, загрузки, плейлист, замена), API —
`hub/app/api/mixes.py` (`hub/API.md`, «Микс дня»). Настройки — `config.yaml` `mixes:` (размер 50, запас 20, веса
генераторов, ≤ 2 песни исполнителя, длина 1:30–10:00) и `.env`: `LASTFM_API_KEY`, `EMBEDDER_URL`, `TIMEZONE`.

### 6.1. Генерация
Каждые 5 минут Хаб смотрит, у кого настал `mix_hour` (5:00 по умолчанию; местное время `TIMEZONE`, по умолчанию
`Europe/Moscow`, — контейнер живёт в UTC) и сегодня ещё не собирали (`mix_settings.last_build_on`), и ставит задачу
`mix_build` (фоновая: приоритет `-10`, как у импорта, — ниже загрузок пользователя, сетевые запросы уступают его
запросам). Нет ни истории (события, загрузки), ни выбранных исполнителей — микса нет. Админ может собрать заново
(`POST /api/mixes/rebuild`, не фоном). Перед сборкой подтягиваются свежие scrobbles Navidrome пользователя.
1. **Генераторы** (параллельно; упавший пишет ошибку в статистику микса, остальные работают):
   - «Любимое» `favorites` — треки профиля с положительным баллом, не звучавшие 7 дней, по баллу;
   - «Тайник» `stash` — свои ♥ и загрузки, не звучавшие 60+ дней или ни разу, в порядке дня (хэш от даты);
   - «Похожее» — `ytm_radio` и `lastfm_similar` по каждому сиду (списки сидов чередуются: первые каждого, вторые…),
     `deezer_radio` по 3 топ-исполнителям;
   - «Незнакомое» — `yandex_similar` по сидам; `similar_artists` — по 3 топ-трека до 15 исполнителей, похожих на 3
     любимых (Deezer `related` + Last.fm `artist.getSimilar`), которых нет в истории;
   - «Новинки» `new_releases` — релизы 10 любимых исполнителей за 30 дней (по 3 трека);
   - «Моя волна» Яндекса `yandex_wave` (M7, раздел 4.1).
2. **Кандидаты:** одна песня — один кандидат (тот же отпечаток из разных источников складывается, у генератора —
   лучшая позиция); что есть в библиотеке — помечается (песня Navidrome, качать не надо).
   **Фильтры:** «Не нравится» (трек по `ref`/песне, исполнитель по `artist_ref` и по имени); версии live, remix,
   караоке, минусовки, каверы, slowed/sped up/8D/bass boosted (`matching/normalize.version_kind`); длина < 1:30 или
   > 10:00. **Знакомое** — трек есть в истории (отрицательный балл — выкидывается; звучал за 3 дня — выкидывается)
   **или** его исполнителя дослушали больше 5 раз (новая песня любимого исполнителя — знакомое); **новое** — ни то
   ни другое (правило «Незнакомого» Яндекса).
3. **Оценка:** `score = Σ_генераторов w_g / log2(позиция + 2) + 1.5·sim + 0.2·популярность`; `w_g` — `mixes.weights`
   (Любимое, радио YTM, Моя волна 1.0; Тайник, Last.fm, похожие Яндекса 0.8; радио Deezer, Новинки 0.7; похожие
   исполнители 0.6), популярность — `min(1, log10(rank Deezer + 1) / 6)`. `sim` — от `embedder` (раздел 4.2):
   лучшие 300 кандидатов по оценке без звука идут в `/similarity`; у кого вектора нет — свежее превью Deezer в
   `/embed`, сборка ждёт векторы до `MIX_EMBED_WAIT_S` (180 с), спрашивая раз в `MIX_POLL_S` (5 с); заодно в
   `embedder` уходят все песни библиотеки (`path`; посчитанные он пропускает). Сервис не ответил — без `sim`
   (в статистике `embedder: down`).
4. **Сборка:** режим пользователя — «Обычный» `normal` 40 % знакомого / 60 % нового (по умолчанию), «Любимое»
   `favorites` 80/20, «Незнакомое» `discover` 10/90; не хватило одной части — добирается другой. Жадно по оценке:
   следующая песня уже взятого исполнителя дешевле на 0.3, больше 2 песен исполнителя нельзя (вместе с запасом).
   Запас — ещё 20 в тех же долях. **Порядок:** первой — сильнейшая знакомая; доли чередуются равномерно (у
   «Обычного» — 2 знакомых на каждые 5); из 4 лучших песен нужной части берётся ближайшая по звуку к предыдущей
   (`/vectors`), исполнитель не подряд.
5. **Название и описание** — LLM (`ai/llm.py`, `LLM_MODEL`; доли цента, в `ai_usage` как `mix`) по 6 главным
   исполнителям, их тегам Last.fm, дню недели и времени суток, «в духе daylist». Без ИИ или при ошибке —
   «Микс дня · пятница» и «Кино, Сплин, ДДТ и другие: 20 знакомых и 30 новых песен».

### 6.2. Скачивание и плейлист
- Песни микса, которых нет в библиотеке, качаются тихо: `download_items` с `query_json.mix = {id, item}` (пакет
  `origin=mix`), приоритет задачи `-10`, фоновый сетевой приоритет; `library.owned.quiet` — не видны в «Загрузках»,
  без уведомлений. Трек уже качается (импорт, другой микс) — песня ждёт ту загрузку (и не считается «скачанной для
  микса»). Явная загрузка того же трека пользователем делает загрузку обычной и видимой (`join_active`).
- Плейлист Navidrome «Микс дня» — один на пользователя (`mix_settings.nd_playlist_id`; удалили в приложении —

  название и описание. В плейлисте — песни микса, которые уже в библиотеке, в порядке микса.

  `mix_sync` (одна на микс, через 20 с): готовые получают песню Navidrome, упавшая (`failed`, `needs_review`,
  `cancelled`) уступает место лучшей из запаса той же части (знакомое/новое), запасная начинает качаться, плейлист
  переписывается, если изменился.
- Таблицы: `mixes (id, user_id, created_at, title, description, mode, nd_playlist_id, status active|closed,
  batch_id, stats_json, closed_at)`, `mix_items (mix_id, position, state active|reserve|failed, familiar, ref,

  (`disliked`, `version`, `duration`, `recent`, `negative_score`; все кандидаты), `embedder`, время.

### 6.3. Удаление при замене (M5)
Новый микс сохранён → прежний микс пользователя закрывается (`closed`): его ещё не начатые тихие загрузки
отменяются, песни с `downloaded_for_mix` (скачаны ради микса) проверяются (`core.remove_unheard`). Песня
**удаляется в корзину** (`library.editor.trash_track`, как удаление ассистентом; `.trash` хранится 30 дней), только
если **никто** из пользователей:
- не слушал её ≥ 30 с (`finish` или `skip` с `position_s ≥ 30` в `play_events`; scrobbles Navidrome там же, как `finish`),
- не ставил ♥ (Navidrome `getStarred2` каждого сейчас), не добавлял в свой плейлист (кроме «Микса дня»),
- не просил скачать явно (у файла есть не тихая загрузка),
- и она не входит в другой действующий микс (по треку или `ref`) или в импорт (`import_items`).

Navidrome хоть одного пользователя не ответил — не удаляется ничего (проверка — при следующей замене). Решение
пишется в `features_json.cleanup` (`trashed`, `kept: listened, starred…`, `nothing`) и не пересматривается; песню,
которую держит только другой микс, и песню, загрузка которой ещё шла при закрытии, проверяет следующая замена.
Песни, которые были в библиотеке до микса, не трогаются никогда.

## 7. Моя волна (T6 — Хаб и PWA, сделано; T7 — приложение)
Код — `hub/app/mixes/wave.py`, API — `hub/app/api/wave.py` (`hub/API.md`, «Моя волна» — контракт, по которому
работают и PWA, и приложение). Бесконечный поток: Хаб выдаёт по 5 треков и подбирает заново после каждого действия.

### 7.1. Сессия и пул
- `POST /api/wave/start {seed?, mode?}` → `{session_id, title, tracks[≤5], pending}`. Сессия — строка
  `wave_sessions` (`id`, `user_id`, `mode`, `seed_json`, `batch_id`, `state_json`) + в памяти профиль вкуса, векторы,
  замок и фоновые задачи; после рестарта Хаба сессия читается из строки, профиль строится заново. 24 ч без запросов —
  сессия кончилась (`404`, клиент начинает новую). Строки не удаляются: у сессии без запросов 7 дней следующий старт
  любой волны очищает `state_json` до выжимки (`{cleared, version, taste_model, gens, started, started_familiar,
  skips, seeds_used, downloads}`; пул, очередь и сыгранное больше не нужны) и ставит `cleared_at` (`wave.clear_old`).
- **Для аналитики** (INSIGHTS.md §6.2–6.4, с 2026-10-31; волна сама этого не читает): строка хранит `origin` (где
  запустили: `home_card`, `track_menu`, `radio`…, словарь — `hub/API.md`), `client` (`pwa`, `pwa-app`, `app/<версия>`),
  `restart_of` (сессия, которую приложение пересоздало после `404`), `taste_model` старта, `request_json` (тело
  `/start` как пришло) и `next_calls` (сколько раз звали `next`). Каждый выданный трек — строка `wave_items`
  (`session_id`, `ref`, `nd_song_id`, ключ вектора, исполнитель, название, `generator` = `top_generator`, `gens`,
  `familiar`, `score`, `sim`, `value` — значение отбора `wave.value`, у сида `null`; `position` — порядок первой выдачи,
  `handed_count`/`last_handed_at` — сколько раз выдан, в т. ч. снова как ещё не начатый в очереди клиента). Запись —
  своей транзакцией после состояния сессии: её ошибка пишется в лог и не ломает выдачу.
- **Пул кандидатов** — генераторы микса (раздел 6.1) с его же фильтрами («Не нравится», версии, длина, слышанное за
  3 дня), оценкой (`build.score`: генераторы, `sim` от `embedder`, популярность) и пометкой «знакомое/новое»:
  - своя волна (без сида) — все генераторы микса по профилю, включая «Мою волну» Яндекса (M7);
  - «Волна по треку» — радио YouTube Music, Last.fm и похожие Яндекса этого трека + радио Deezer его исполнителя;
    сам трек играет первым (`generator: seed`);
  - волна по исполнителю — радио Deezer исполнителя, его топ и радио YouTube Music двух его топ-треков;
    по исполнителю Navidrome (`seed.nd_artist_id`, «Радиостанции» приложения) — ещё его песни из библиотеки
    (генератор `artist_songs` «Песни исполнителя», вес 1,2; до 60 песен из его 30 альбомов, `getArtist`/`getAlbum`),
    исполнитель Deezer — по записи каталога одной из этих песен, иначе поиском по точному имени; не нашёлся — пул из
    песен библиотеки и радио YouTube Music двух из них.
- Источники отвечают с разной скоростью: запрос ждёт их `WAVE_WAIT_S` (8 с) или пока в пуле не наберётся 20
  кандидатов, остальные вливаются в пул фоном (замок сессии). Пул < 25 — фоном радио следующих трёх сидов профиля
  (по кругу). Новые кандидаты сразу идут в `embedder` `/similarity`, лучшие 60 без вектора — его очередь (превью Deezer).

### 7.2. Пересчёт после каждого действия
`POST /api/wave/{id}/next {played, queued}`: события с прошлого раза пишутся в `play_events` с `context
wave:<id>` (событие, которое клиент уже прислал через `/api/plays/events` с тем же `event_id`, получает этот context),
затем:
- `start` — трек сыгран: больше не выдаётся; последние 50 сыгранных — для правила исполнителя;
- `skip` раньше 30 с и «Не нравится» — исполнитель −0,6 за каждый такой пропуск в сессии, трек — в «отрицательные»;
- `finish` и ♥ — трек в «положительные», его радио YouTube Music вливается в пул (генератор `session_radio`, вес 1,2);
  `finish` трека, которого нет в библиотеке, — тихая загрузка (`query_json.wave`, как у экономного импорта: не видна
  в «Загрузках»; ♥ качает сам клиент, как всегда);
- «Не нравится», поставленное где угодно (`/api/dislikes`), учитывается на следующем запросе.

**Отбор 5:** значение = оценка микса − штраф исполнителя + 1,0 × (косинус к центру «положительных» сессии −
к центру «отрицательных»; векторы `embedder` `/vectors`, кэш в памяти) + 0,3 треку из `queued` (чтобы не менять
очередь из-за мелочи). Жадно по значению с долей знакомого режима (как у микса); **исполнитель не чаще раза в 8
треков** (с учётом сыгранных; исполнитель волны по исполнителю — не чаще раза в 3, `State.seed_artist`); если иначе нечего — правило уступает, но не один исполнитель подряд. Ответ
**заменяет `queued`** у клиента; не попавшие в ответ треки очереди возвращаются в пул. Клиент зовёт `next` на старте
каждого трека волны и после ♥ — то есть поток пересобирается после каждого действия (у Яндекса — не реже раза в 5
треков). Файлы выданных треков Хаб сразу подбирает (`/api/listen/prefetch`), треки играют потоком
(`/api/listen/stream`).

### 7.3. Где видно
- **Живое пятно «Моей волны» — только на компьютере в браузере** (2026-11-07). На «Главной» PWA на компьютере (`STANDALONE` и
  `(min-width: 1024px) and (hover: hover) and (pointer: fine)`, реактивно — `lib/desktop.ts`: `isDesktop()` / `useDesktop()`) «Моя волна» —
  **«герой» страницы** (`components/WaveHero.tsx`): первый блок под приветствием, выше «Микса дня». Без рамки и фона карточки: мягкое
  светлое пятно светится прямо на фоне страницы (холст `min(1100px, 100vw − 32px)` × 340 px шире колонки, к краям гаснет радиальной
  маской), по центру поверх него — «Моя волна», подпись-состояние и под ней белая круглая кнопка (как в мини-плеере): ▶ запускает волну, ⏸ ставит плеер страницы
  на паузу, ▶ на паузе продолжает её (не перезапускает), на запуске — индикатор; перезапуска волны из героя нет.
  Везде остальное — в приложении (`EMBEDDED`), в мобильном браузере, на планшете и в узком окне, а также в «Каталоге» на любом
  устройстве — прежняя простая карточка (`components/Wave.tsx`, `WaveCard`): ни WebGL-контекста, ни Web Audio там нет. Приложение
  пятна не показывает вовсе (ранний вариант с GL-пятном в приложении убран, 1.14.7).
  Вид пятна — один фрагментный шейдер GLSL ES 1.0 (`web/src/lib/waveGlow.ts`): контур медленно перетекает, внутри светлые нити.
  Колец, лучей и толчков на битах нет. Всё движется экспоненциальным сглаживанием
  `x += (цель − x)·(1 − e^(−dt·rate))`: пауза ↔ игра `P` (rate 0,7/с, ~3 с; на паузе пятно примерно на 40% меньше (радиус .19 против .31), движется медленнее, светлые
  нити почти гаснут, яркость ×0,88, край мягче — цвета остаются насыщенными, серого нет), громкость `E`
  (только сглаженный RMS, атака 1,2/с, спад 0,6/с, без детекции битов — пятно «дышит»), цвета из обложки текущего трека
  (rate 0,5/с; яркость и насыщенность подтянуты, серая обложка — цвета по умолчанию жёлтый/малиновый/красный), ♥ волны —
  тёплое свечение `W` (~1,5 с вверх, затем вниз), пропуск — форма `S` плавно переезжает на +2,1 (rate 0,4/с). Время фазы `T`
  интегрируется на CPU (`dt·(0,03 + 0,045·P)`), поэтому смена `P` не сдвигает форму рывком. «Уменьшить анимацию»
  (`prefers-reduced-motion`): время ×0,3, громкость не используется. Рендер в половинном разрешении, ~30 кадров/с, стоп вне экрана,
  в фоне и при скрытой вкладке; без WebGL — неподвижный мягкий градиент. Цвет фона шейдера (`BG`) — фон страницы (`body`), он следит
  за темой.
  - **PWA** (`components/WaveGlow.tsx`, `lib/waveAudio.ts`): ♥ и пропуск — из `onPlayEvent` (контекст `wave:`). Громкость —
    `AnalyserNode` на `<audio>` страницы (`createMediaElementSource`), **подключается только пока смонтировано пятно, то есть на
    компьютере**: после подключения звук идёт только через `AudioContext`, поэтому элемент подключается, лишь пока он играет,
    контекст уже `running` и источник того же origin; на каждый `play` контекст возобновляется. На телефоне, планшете, в приложении
    и в «Каталоге» `<audio>` не трогается вовсе. Выключить анализатор: `localStorage['hm-wave-audio'] = '0'`. Без анализатора пятно
    просто спокойнее (без «дыхания» от громкости).
- **PWA** (`web/src/lib/wave.ts`, `components/Wave.tsx`): карточка «Моя волна» в «Каталоге» под «Миксом дня», в меню
  «⋯» трека — «Волна по треку» и «Волна по исполнителю». В браузере меню доступно также в мини-плеере
  и у каждого трека очереди; в полном плеере есть отдельная кнопка «Моя волна по треку».
  Волна по песне доступна также для файлов из поиска (`file:<provider>:<id>`), включая песни без записи
  в каталоге: Хаб берёт название и исполнителя из сохранённого результата поиска, выбранный файл играет
  первым без подмены другой версией. В строке результата поиска файлов тоже есть меню «⋯».
  Запуск создаёт новую очередь даже для уже играющего трека, выключает перемешивание и ставит выбранную
  песню первой. В браузере играет мини-плеер страницы (`context wave:<id>`, значок волны у исполнителя):
  события его треков идут в `next` (`onPlayEvent` в `lib/plays.ts`), ответ заменяет
  оставшиеся треки (`replaceUpcoming` в `lib/listen.ts` — дописывание очереди; кончившаяся очередь играет дальше).

  ID и название волны и ещё не подтверждённые события из локального хранилища текущего аккаунта (после `/api/me`);
  при возобновлении трека запросы `next` продолжаются для той же сессии. Запрет autoplay оставляет плеер на паузе.
- **Внутри приложения** (решение T6): плеер в приложении один — нативный, и PWA ничего не играет сама. Мост

  1.2.0–1.5.x (`playQueue` без `playWave`) кнопок волны нет (5 треков без продолжения хуже, чем ничего); до 1.2.0 волну
  играет мини-плеер страницы, как в браузере.
- **Приложение** (T7, `android/…/homemusic/HubWave.kt`, логика — `Wave.kt`): волна ведётся на плеере сервиса, поэтому
  идёт и в фоне. `next` — на `start` каждого трека волны, после его ♥ и «Не нравится» (и из меню, и кнопкой в плеере);

  тем же сидом и режимом (трек-сид не повторяется). Кончилась очередь — заглушка «Подбираем следующую песню…»

  микса Хаба, нет микса — «Что вы слушаете?»; ▶ — весь микс, с нескачанными треками, `context mix:<id>`).

## 8. Умное перемешивание (Smart Shuffle — Хаб, PWA и приложение, сделано 2026-11-07)
Код — `hub/app/mixes/smart.py` (сессия, подбор), `hub/app/mixes/smart_order.py` (чистые правила: порядок, соотношение, выбор
сидов), API — `hub/app/api/smart_shuffle.py` (`hub/API.md`, «Умное перемешивание»). Копия поведения Spotify Smart Shuffle
для плейлистов и «Понравившихся»; вся логика на Хабе, клиенты только показывают.

### 8.1. Что копируем у Spotify (ресёрч) и что решили сами
- Кнопка перемешивания ходит по кругу: **выкл → перемешивание → умное перемешивание → выкл**; у третьего режима свой значок
  (перемешивание с искоркой). Настройка «Умное перемешивание в режимах» (PWA — «Ещё», приложение — настройки, по умолчанию
  включена) убирает третий режим из круга.
- Только **плейлисты Navidrome и «Понравившиеся»**. Альбомы, исполнители, Микс дня, волна, поиск — кнопка работает как
  обычное перемешивание (режим «умное» там не предлагается, выбор запоминается и вернётся у следующего плейлиста).
- Между своими песнями идут **рекомендации «в настроении плейлиста»**: в плейлисте больше 15 песен — одна на каждые **3** своих
  (цифра Spotify), в плейлисте до 15 песен включительно — одна на каждые **2** (цифры Spotify нет, решение владельца);
  плейлист из 1–2 песен получает одну. Первым всегда играет свой трек (нажатый или случайный). Плейлист не меняется.
- У рекомендации в плеере, мини-плеере и очереди ✨ у исполнителя, в плеере — плашка «Рекомендация на основе „<плейлист>“»
  (для «Понравившихся» — «на основе любимых песен») и кнопки **«+»** (в плейлист; в «Понравившихся» — ♥; трек, которого нет
  в библиотеке, скачивается и после импорта попадает в плейлист; ✨ пропадает) и **«−»** («не рекомендовать в этом плейлисте»:
  трек сразу пропускается и больше не предлагается для этого плейлиста или «Понравившихся»; не глобальное «Не нравится»).
- Выключение умного режима убирает рекомендации из оставшейся очереди и возвращает исходный порядок от текущего трека
  (свои песни, ещё не сыгранные, — по порядку плейлиста, начиная со следующей за текущей); включение посреди воспроизведения
  вставляет рекомендации после текущего; повторное включение даёт **свежую подборку**.
- **Порядок своих песен — «Fewer repeats»** (инженерный блог Spotify, 2025): несколько (20) случайных перестановок, у каждой
  «устарелость» — штраф за недавно слышанные песни (по истории пользователя во всех контекстах: `finish`, пропуск после 30 с,
  scrobbles Navidrome; штраф песни `1/(1+дни)`, делённый на `1 + позиция/12`, то есть чем недавнее слышал и чем раньше стоит, тем
  больше), берётся самая свежая; песни одного исполнителя разнесены (идея Spotify 2014: k песен исполнителя ставятся с шагом
  1/k списка со случайной фазой, потом соседи одного исполнителя меняются местами). Обычное перемешивание не тронуто.

Места, решённые без данных Spotify: 1:2 для коротких плейлистов; 20 перестановок и вид штрафа (`1/(1+дни)` × спад по позиции) —
публикация Spotify не даёт формулы; вес звукового сходства с центром плейлиста 3,0 (при весе 1,5 у сходства со вкусом);
«свежесть» повторного запуска — штраф 3,0 трекам, которые прошлые запуски того же контекста предложили за последние 3 дня
(их хватает, чтобы не повторяться, пока есть из чего выбрать; иначе повтор лучше пустого места); окно «впереди» — 3 рекомендации
(при каждом старте трека Хаб дозаполняет места до 3 вперёд, поэтому реакция на пропуск/♥ действует на подбор со следующих
мест); «+» в «Понравившихся» делает клиент своим обычным ♥, Хаб только отмечает; «−» не имеет «отменить»; кнопки уведомления и
виджета в умном режиме просто выключают его; сессия приложения не переживает перезапуск процесса (очередь остаётся, ✨ уходят);
в приложении очередь со страницы не длиннее 500 песен (как обычное перемешивание «Понравившихся») и тап по песне плейлиста умный
режим не запускает.

### 8.2. Сессия и порядок
- `POST /api/smart-shuffle/start {context, songs[], current?, title?, origin?, client?}`: `context` — `liked` или
  `playlist:<id Navidrome>`; `songs` — песни списка в его порядке (плейлист: новые в конце; «Понравившиеся»: новые первыми; id песни
  Navidrome, либо ref каталога для ♥ без файла); `current` — нажатая/играющая песня, она первая. Ответ: `own` — порядок своих
  песен (все сразу, это дёшево), `recs` — рекомендации для первых мест (по 3 вперёд), у каждой `after` (после какой своей песни
  вставить) и `slot`; рекомендации хранятся и считаются по месту, поэтому большие списки («Понравившиеся» до сотен песен) не
  считаются целиком.
- Места: рекомендация `k` стоит после своей песни номер `per·(k+1)`, `per` = 3 (> 15 песен) или 2; всего `max(1, n // per)`.
- `POST …/{id}/next {played[], at}`: события реакций (`played`, как у волны, одни и те же `event_id` идут и в `/api/plays/events`)
  и место плеера (`at` — своя песня, на которой он или которую прошёл последней); Хаб дозаполняет ещё не занятые места до 3
  впереди. Ответ — только новые `recs`; уже выданные рекомендации окончательны. Нет подобранного — `pending` (спросить позже).
- `…/{id}/hide {ref|nd_song_id}` — «−»; `…/{id}/add {ref|nd_song_id}` — «+»: плейлист — песня библиотеки добавляется в плейлист
  Navidrome, трека каталога нет — загрузка в плейлист (`POST /api/downloads` с `playlist_id`, как «Скачать в плейлист» — виден
  в «Загрузках»), «Понравившиеся» — Хаб только отмечает (`status: liked`), ♥ ставит клиент.
- Сессия — `smart_sessions` (состояние для продолжения после рестарта Хаба; 24 ч без запросов — `404`, 7 дней — состояние
  очищается до `{cleared}`, строка и `smart_items` остаются), выданные рекомендации — `smart_items` (позиция, место, генераторы,
  счёт, звук, значение отбора, состояние `handed`/`added`/`hidden`), скрытые «−» — `smart_hidden (user, context, fingerprint)`.
  Миграция `a3c8e5f17b92`.

### 8.3. Подбор рекомендаций
Сессия — это `wave.Runtime` со своей строкой (`wave.Runtime.save`, `blocked`, `download_finished=False`): пул, фильтры
микса (`build.keep`: «Не нравится», версии, длина, слышанное за 3 дня), оценка `build.score` и обучение по событиям
(`wave.learn`, и v1, и v2) — общие с волной.
1. **Сиды** — до 10 песен списка (`smart_order.choose_seeds`): 3 новейших (плейлист — с конца, «Понравившиеся» — с начала), остальные
   случайные, исполнители разные, пока есть из кого.
2. **Кандидаты** — генераторы микса по этим сидам: радио YouTube Music, Last.fm, похожие Яндекса, радио Deezer двух главных
   исполнителей списка и «Тайник» (свои забытые ♥ вне списка); `WAVE_WAIT_S` ждёт источники, остальные вливаются фоном; пул
   < 25 — фоном радио следующих сидов списка по кругу. Подходят и песни библиотеки вне плейлиста, и новые треки каталога
   (играют потоком, `/api/listen/stream`, как у волны).
3. **Отсев:** песни списка (по id, ref и «артист — название»), «Не нравится», скрытые «−» этого контекста, слышанное за последние
   дни (правило микса). Одна и та же рекомендация не уходит дважды за сессию.
4. **Оценка:** `value` волны (оценка микса − штраф пропусков исполнителя + близость по звуку к тому, что понравилось в сессии, −
   к пропущенному) **+ 3,0 × близость по звуку к центру песен списка** (`embedder` `/similarity` с песнями списка как профилем;
   у трека без вектора — медиана известных) **− 3,0** тому, что предлагали прошлые запуски контекста (свежая подборка). Превью
   лучших кандидатов без вектора ставятся в очередь `embedder` (в следующих подборах они уже с вектором).
5. **Выбор на место:** лучший по значению, чей исполнитель не встречался в последних 7 рекомендациях и не равен исполнителю
   своих песен по обе стороны места; нечего выбрать — правило 7 уступает, правило соседей нет (`smart_order.pick_rec`).
6. **Обучение:** ранний пропуск рекомендации (< 30 с) — минус исполнителю и звуку трека, дослушал / ♥ / «+» — плюс (для v2 «+»
   добавляется в веса сессии, радио понравившегося вливается в пул, `wave.learn`); «−» — как ранний пропуск и скрытие.

### 8.4. События и аналитика
События своих песен идут как раньше (`playlist`, `liked`), рекомендации — с контекстом **`smart:<сессия>`** (Хаб проставляет его и
событию, которое клиент прислал через `/api/plays/events` под другим контекстом, например `queue`). Профиль вкуса считает `smart:`

подпись в PWA `format.ts`); эксперимент P5 и остальное — без изменений. В `/healthz` — capability `smart_shuffle_v1`.

## 11. Проверка
- Хаб: тесты на каждый генератор с фикстурами ответов (respx), на оценку и сборку (50 песен, доли, ≤ 2 исполнителя),
  на правило удаления (каждое «нельзя удалять»), на сессию волны; живой прогон сборки микса на рабочем Хабе.
- `embedder`: тест API на коротком синтетическом звуке; замер скорости — раздел 4.2.
- Приложение: unit-тесты определения `skip`/`finish`, очереди событий, дописывания очереди волны; эмулятор.

## 12. Исследование (2026-10-22, кратко)
- **Spotify:** Discover Weekly — коллаборативная фильтрация по плейлистам + CNN по 30-секундным фрагментам для новых
  треков; Daily Mix — кластеры вкуса, любимое + рекомендации; daylist — несколько раз в день по тому, что слушают в это
  время, названия из «дескрипторов»; 2026 — Prompted Playlist, Taste Profile. Вкус в окнах ~6 мес / 1 мес / 1 нед.
  API рекомендаций закрыт для новых приложений с 27.11.2024.
- **Яндекс:** «Моя волна» — селекторы (сотни тысяч кандидатов) → фильтры (исполнитель не чаще 25 треков) → CatBoost →
  трек; пересборка после каждого действия, не реже чем раз в 5 треков; «Незнакомое» — трек не слышан, исполнитель
  слушан ≤ 5 раз; с 2026 — трансформер ARGUS. «Плейлист дня» ~60 треков, «Дежавю», «Премьера», «Тайник».
- **Open source:** ListenBrainz (Daily Jams: CF → слушанное, но не 60 дней → ≤ 2 исполнителя → 50 → перемешать),
  Navidrome Instant Mix и плагины, AudioMuse-AI (MusiCNN + CLAP, «Sonic Fingerprint» — центр векторов любимого с
  полураспадом 30 дней), Explo (ListenBrainz → yt-dlp → плейлист). Ни один не знает треков вне библиотеки и
  современного русского рэпа (ListenBrainz: похожих на «Кино» — 100, на MACAN — 0).
- **Источники похожести, проверено вживую:** радио YouTube Music — лучшее (50 точных треков, 2,5 с); похожие Яндекса
  без токена — в малоизвестное; Deezer радио/похожие — без ключа; ListenBrainz `metadata/lookup` теперь требует токен.
- **Модели:** MuQ-MuLan (CC BY-NC), LAION-CLAP (CC0), Essentia Discogs-EffNet (CC BY-NC), CLaMP 3 (текст на 100
  языках). Для треков вне библиотеки — превью Deezer 30 с.


Волна по исполнителю трека: `seed` принимает `ref` или `nd_song_id` вместе с `by_artist: true`. Хаб разрешает исполнителя и сохраняет в ответе `artist_ref` / `nd_artist_id`; если исполнитель не найден, возвращает 404. Личная волна запускается без `seed`.
